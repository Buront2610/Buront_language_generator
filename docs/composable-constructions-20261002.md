## 1. 過去助動詞の共通判定

`grammar-scope.ts` の `isPastAuxiliary` を `facts.ts` と謙遜構文で共有します。GiNZAでは「運んだ」の過去助動詞が lemma「だ」でも `Inflection=助動詞-タ` になり、終止コピュラ「だ」の `助動詞-ダ` と区別できます。仮定形は過去の根拠にしません。

謙遜の適用は表記末尾「ただけだ」ではなく、対応する達成述語に結び付いた過去AUX→「だけ」→終止コピュラを原文tokenから検査します。既存の有限達成語彙、文頭の謙遜、主体・肯否・時制・引用・予定・共同主体のガードを残します。「運びたかっただけだ」は過去の願望であって達成ではないため、達成述語に結び付いた願望AUX「たい／たかっ」はこの謙遜構文の適用を遮断します。これは別途発見した旧版にも存在する抜けへの局所的な安全修正で、factsや共有作用域全体の意味を変更していません。

- 許可: 「大したことはしていない。荷物を届けただけだ。」「大したことはしていない。荷物を運んだだけだ。」
- 棄権: 「運ぶだけだ」「運ばなかっただけだ」「太郎が運んだだけだ」を後続させた入力
- 取得スクリプトと実GiNZAの未編集fixture: `test/fixtures/capture-ginza-discourse-recognition.py`、`ginza-discourse-past.json`、`ginza-discourse-context-boundaries.json`、`ginza-discourse-desire.json`

## 2. 理由の読み取り範囲と書き込み範囲

旧版は理由本文全体を「何故なら＋本文」へ置換するため、理由内部の合法な語彙編集まで競合として落としていました。新版の明示的な操作は次のとおりです。

- 読み取り・根拠: 主張、理由全文、そのtoken ID、文法条件、出典
- 書き込み: 理由開始位置への幅0の接頭辞挿入
- 本文: `prefix_source_body` 操作の `bodySourceSpan` で原文を参照
- 合成許可: `independently_verified_rewrites`。本文内の局所編集は単独でも既存の `validateRewrite` を通るものだけ

全編集を同じ原文座標に束縛し、一度だけ実現します。生成文字列を次の規則の入力へ戻しません。幅0の登録prefixは同じ位置から始まる本文編集より先に実現します。重なった置換、二重prefix、本文境界をまたぐ編集、本文内の未承認な別構文置換は引き続き拒否します。読み取り範囲が広いだけで語彙編集を禁止することと、実際の書き込み競合を分けました。

「私はこの方法を選んだ。速度が重要だからだ。」では「速度→速さとスピード」が単独の語彙規則として実際に許可されます。語彙のみ、理由導入のみ、両者合成の3通りを同じ独立検証で確認しました。理由のみは部分構成を分離した明示的なablationです。通常候補が常に全ての部分集合を生成・表示するという主張ではありません。実際の全文・表示順位は[比較記録](composable-constructions-evaluation-20261002.md)を参照してください。

構文候補の出力spanも、prefix、局所置換、原文のコピー部分に分けます。prefixの出力を幅0の原文位置へ、語彙置換を元の語へ、残る本文を正確な原文範囲へ追跡できます。

## 3. 認識と実現の分離

`createDiscourseRecognizer` は出力語句・濃さ・系列を参照せず、関係の種類、節範囲、根拠token、主体や否定・時制・条件・推量などの観測条件、明示性、入力hashとparser版を返します。`realizeDiscourseRelation` がその関係に使える登録形式を選びます。例えば「しかし」の明示関係は標準でも認識されますが、「だが」の実現は濃いめに限られます。

この分離で裸の「が／から」から任意の対立・因果を推測しません。検証側はシリアライズされた関係や生成時のキャッシュを信用せず、原文IRからもう一度認識・束縛し、出典・条件・操作・出力全文と照合します。これは元の解析を入力とする有限証明であり、任意の言い換えを別の意味モデルが判定したものではありません。

独立レビューでは、GiNZAが改行だけをROOT SPACEの文にする場合、疑問文・推量文の後でもその改行を主張として扱う既存の抜けを発見しました。空白だけの直前文は根拠にならないとして棄権するよう狭めました。前の非空白文を探索して適用を広げてはいません。過去「だ」の意図した修正と、この安全性の強化を、旧認識との差として別記しています。旧179fixture×2濃さの358比較は全て認識が一致しました。最初の新20診断では過去「だ」の2追加、空白文の4除外だけが差です。追加の願望6診断では過去願望の2例だけを新たに遮断します（[認識比較](../artifacts/composable-constructions-20261002/recognition-parity.json)）。

## 4. 診断と互換性

入力hash、node ID、構文ID、計画ID、候補ID、原文範囲とともに、次の実際の段階を記録します。

- `relation_not_recognized`: 現在の認識器が根拠を束縛できなかった
- `scope_blocked`: 引用・推量・疑問などの作用域または採用範囲が不適合
- `unsupported_form`: 関係は認識できるが濃さ・系列・登録出典に対応する形式がない
- `edit_conflict`: 実際の競合する編集を除外
- `planned`、`verified`、`verification_rejected`、`selected`、`not_selected`

最終の独立検証後に候補段階の診断を更新し、仮選択を採用済みと誤表示しません。診断自体を変換許可や意味保持の証拠には使いません。局所構文は未認識を一括した `no_registered_local_source_binding` とし、実装が観測していない細かい理由を創作しません。

ConstructionProgramはv2、談話構文もv2です。操作・関係・診断のJSON Schemaを生成し直しています。旧プログラムを新しい編集代数として読み替えず、旧ロックは拒否します。replayもengine hashと親候補の独立再検証を必要とし、ロックした本文・prefix・関係・出典の改変は拒否します。

評価の変更種別は人称・句読点、語尾、語彙、談話標識、節内構造に分けます。「何故なら」を足すことを段落構成の変更には数えません。既存35入力は回帰用として維持し、制御対照とコード凍結後の未使用入力は別集計です。

## 5. 既存の選好学習への配線

`npm run train:preferences -- ...` は `BURONT_PYTHON` を優先し、未指定ならWindowsの `.venv/Scripts/python.exe`、それ以外の `.venv/bin/python` を使います。shell文字列を作らず、引数・空白入りパスをそのまま子プロセスへ渡します。Linuxでは固定Pythonで実起動し、Windowsのパス分岐はstubで検証しています。Windows実機での起動済みという意味ではありません。

通常の比較exportは既存の `{comparisons, preferences}` 形式です。保存済みreview画面の `{pack, answers, history}` は `npm run prepare:preferences -- review-export.json comparisons-with-labels.json` で同形式へ明示変換できます。既存の44特徴 `output-text-dense-v2` を使用し、最新の明示回答だけを取り込み、pilot区分を維持します。既存ファイルは上書きしません。train/validation/test区分を自動で作ることはしません。

保存されている現行63組には人のラベルがありません。旧224組は特徴形式が古いため、そのまま学習できません。今回ラベルや学習済みモデルは作成せず、S/Qは未学習ならnullのままです。詳細は[注釈・学習手順](../assets/annotations/README.md)を参照してください。

## 長文での実測と局所最適化

217組の主張・理由を含む4,991scalarの反復文でも検査しました。最初の実装は合法な合成候補が増えたことで、生成＋独立検証が基準版より遅くなり、既定30秒のAPI期限を超えました。失敗した測定を[修正前記録](../artifacts/composable-constructions-20261002/preoptimization-performance.json)に保存しています。

同じ解析・資産・入力によるCPU profileでは、構文の述語を探す際にtoken範囲とfact範囲を毎回SHA256化する既存処理が主因でした。範囲のstart/endの数値一致へ置き換えるだけで、同じ判定を保ちます。候補を減らしたり、検証を省略したり、生成側のキャッシュを検証へ渡したりはしません。[基準との比較](../artifacts/composable-constructions-20261002/dense-baseline-comparison.json)と[最終長文測定](../artifacts/composable-constructions-20261002/independent-performance.json)に候補数・時間・RSS・出力対応を記録します。同一条件の最適化前後で、全8候補・選択結果・計画・検証・span・IR・診断のhashが一致しました。直接実行は生成31.38→15.61秒、独立検証10.22→3.58秒。最終API実測は4,991文字の談話密集文22.312秒、反復5,000文字12.611秒、数量・引用を含む4,928文字6.890秒で、全て既定30秒以内に完了しました。単一の反復負荷の成功は任意の最大長入力の保証ではありません。
