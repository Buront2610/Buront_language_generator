# 明示された主張・理由の型付き構造生成（実験・既定OFF）

## 今回増えた能力

原文「主張。理由からだ／からです。」から、理由節を前へ移して「理由から、主張。」を実現する。名詞・動詞を完成文の一覧に照合する方式ではない。原文をGiNZAで解析し、主張と理由の向き、節、主体・対象、述語、助動詞・否定・時制などを原文のtoken ID／Unicode scalar座標へ束縛する。既存の語彙編集を、移動する節の内部にも元の座標で合成できる。

同じ関係には「主張。何故なら理由からだ。」も用意する。後者の接頭辞自体は従来からある能力であり、今回の新機能とは数えない。新しい能力は、理由節の前置・主節との接続、およびその構造の中への原文基準の局所編集である。

これは手書きの限定された日本語因果文法である。学習した構文モデル、未知の動詞を新たに活用する生成器、自由な全文生成ではない。述語を辞書形へ戻さず、既に原文にある活用済みの述語と演算子のまとまりを射影する。このため新しい動詞や名詞に、達成動詞のホワイトリストや原文完全一致なしで対応する。

## 使い方

ビルドと通常のローカルサーバー起動は従来どおり。

```sh
npm run build
npm start
```

認証済みの `POST /api/v1/generations` に、既存の要求とともに次を付ける。

```json
{
  "source": "私は作業を続けた。速度が十分だったからだ。",
  "task": "rewrite",
  "contextMode": "faithful",
  "noveltyMode": "blend",
  "intensity": 2,
  "series": "all",
  "backend": "structured",
  "clientRevision": 0,
  "seed": "structural-demo",
  "experimentalStructural": true
}
```

`experimentalStructural` はbooleanのみ。省略／falseでは従来の経路のまま。濃さ1では構造生成しない。画面の「明示理由の組み替え（実験・既定OFF）」でも有効化できる。設定変更時には古い結果・要求を無効化する。`GET /api/v1/capabilities` が対応範囲、既定OFF、文法版を返す。既存の `/api/convert` はこの実験を有効化しない。

coreでも通常の `generate(request, analysis, assets)` から実行する。CLI専用の孤立した生成器ではない。APIは通常のCoordinator→worker→GiNZA解析→候補生成→独立最終検査→表示選択を通る。

## 契約と実現

`packages/core/structural.ts` と `packages/contracts/` が実装の中心。

- `StructuralProgram.version = 1`
- `grammarVersion = explicit-reason-slots-v1`
- `authoring = handwritten-source-projection`
- `clauses`: 原文node ID、原文範囲、型付きslot、原文から抽出したFactのスナップショット
- slotの型: agent／patient／recipient／location／predicate／operator／case／adjunct／punctuation／gap
- slotは原文座標、token ID、Fact ID、保護値IDを持つ。完成した入出力文は保存しない
- `bindings`: 原文だけから認識した明示理由、claim/reasonのnode ID、採用する実現ID
- `sourceOrder`: 原文順。`emissionOrder`: 実際の出力順。この2つを混同しない
- `lexicalEdits`: 従来からある出典付き編集。すべて元入力の座標で実行し、生成済み文字列への二度目の置換はしない

理由先行では、依存関係で確認した終端の説明コピュラ（から**だ／です**）と直後の句点だけを読点へ置換する。たとえば「原因**だった**から**だ**」の前の「だった」は残る。「凍結していなかった」「低くなかった」などの否定・アスペクト・過去も残る。

語彙編集が削除／変更する文法境界をまたぐときは合成しない。理由先行の主節には、既存の任意の強調語尾 `ending-insistence` を重ねない。因果接続と「からな」を二重に積むことを避けるためで、速度→速さとスピード、私→俺などの独立した編集はそのまま許可する。

複数の独立した組は一つの原文計画へ入る。組ごとの全組合せは作らず、理由先行パターン／主張先行パターンと最大6個の既存語彙編集案、無編集の射影案だけを使う。構造案は最大14、全候補プールは従来どおり36、表示は最大3。

## 出典の扱い

「何故なら」の表面は既存登録済みの `post_02421_ef97fdc26a351d5a_9490` に結び付く。元投稿と対象系列の利用条件も従来どおり確認する。

「理由から、主張」という並べ替えは手書き文法であり、この語録に学習済み構文として帰属させない。そのbindingの `evidenceIds` は空配列。合成した語彙編集は各自の実出典を持つ。文法操作であることと、ブロント風の部品に出典があることを区別する。

## 独立検証

`validateStructural` は生成器の宣言を証拠にしない。原文IRから節、slot、Fact、明示理由をもう一度組み立て、移動の適用条件も再検査する。

- slotの役割・座標・token・人物・数値・否定・時制・帰属のスナップショットを再照合
- 主張／理由の向き、文法版、許可された実現、重複する組を検査
- 原文範囲を一度ずつ使うことと、許可された出力順を別々に照合
- 局所編集を既存 `validateRewrite` で原文から独立検証
- すべての出力片を原文slot／許可編集へ対応付け、返却本文とplanの一致を検査
- 数量は移動前の各節と移動後の同じ節を対応付けて比較。全文の数量出現順が変わったことだけで失敗させず、別の節への移し替えも認めない

初期検査 `V-structural` の後、APIの最終段階でも `S-structural-projection` が再検証する。これは出力全文を別途解析して自由な意味同値性を判定する方式ではない。有限文法の原文再束縛と文字列射影の検査である。検査通過は文体品質・自然さ・面白さの評価ではない。

replayはopt-in時にmanifest schemaVersion 2と文法版を記録。未知の版、flag型不正、版不一致は失敗させる。原文、解析器、engine、assets、候補集合のハッシュも従来どおり検証する。nodeを固定した再生成では、そのnodeに関係する理由bindingも固定し、別の構造へ文字列だけ移植しない。

## 有限の適用範囲と残る制約

現在の理由認識は、隣接した独立文の「主張。理由からだ／からです。」という明示形が中心。理由の推定、人物の補完、達成の創作、引用された内容の事実化はしない。入力内の別の文にある引用や数値は背景slotとして保持できるが、引用内の理由自体を移動しない。

GiNZAの粗いUD品詞がNOUN/ADPへ揺れた場合でも、原文ROOTの細粒度tagが「動詞-一般」で終止形活用を持ち、そのROOTに属する「から」が「助詞-接続助詞」、直後に終端の説明コピュラがある場合は、実験経路だけで明示理由を認識できる。原文tokenを改変せず、動詞名ごとの例外も作らない。「駅からだ」「三時からだ」などの格助詞はこの条件を満たさない。

なお、GiNZAが「運ばない」を「運ば」＋別ROOTの「ない」という二述語へ分ける場合、現行IRでは主語と否定が別Factへ分裂することがある。この場合は主体を推測して結合せず、理由前置を控える。今後の述語演算子bundleの統合課題である。

移動については認識より狭く制限する。

- 引用・条件・予定・推測・疑問など、閉じた作用域を確立できない組は移動しない
- 実際の照応語や談話接続がある組、重なる理由の連鎖を移動しない。判定は形態素の語単位なので「彼岸花」「またたく」「事実は」を文字列の一部だけで照応語扱いしない
- 主張の主体が省略され、前置する理由に明示主体がある場合は移動しない
- 後続の実質節を末尾まで調べ、照応表現または主語省略があれば移動しない。途中の天気などの話題を人物参照の安全なリセットと推定しない
- この制限は一般的な照応解析が完成したことを意味しない。現状の安全な対象を限定するための保守的な条件である
- 改行などのgapも原文節のslotとして一度ずつ保持する。節先頭の空白が節とともに前へ移ることがあり、組版の最適化は未実装

移動できなくても、明示理由を「何故なら」で提示する従来型の実現や、独立して適用できる語彙編集は候補になり得る。候補の多様性は、変更した関係の実現ID・元の節と出力順の対応・内容語編集のfingerprintで比較し、無関係な未変更背景で差を薄めない。品質と安全性が同率なら「移動＋内容語編集」を実現した候補を先に見せる。これは操作の組合せを確認できるようにするbooleanの表示方針であり、編集数の報酬や文体の良さの点数ではない。

語彙一般化の確認と、自然なブロント文体が得られることの確認は別。S/Qは未学習ならnullのままで、手書きの見せ方優先順位を学習済み品質点に見せかけない。

## 検証方法

```sh
npm run typecheck
npm test
node --test test/v1/structural-generation.test.js
node --test test/v1/api.test.js
```

開発テストは実GiNZAによる動詞・形容詞・名詞述語、否定、過去、人数／数値、Unicode scalar、複数組、局所編集、照応対照、21種以上のplan改ざん、flag OFF、replay、API表示選択、固定再生成を扱う。テスト件数を文体品質の根拠にしない。独立に固定したsource-only入力の評価結果と、開発時に使った例は分けて報告する。新しい教師対やLLMによる品質判定は使っていない。
